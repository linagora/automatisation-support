# Project structure

This document explains the current structure of the `automatisation-support` backend project.

## Main folders and files

### `docs/`

Technical documentation for the project.

This folder is used to document:

- the global support automation pipeline;
- the scope of this repository;
- Mermaid diagrams;
- architecture decisions;
- explanations useful for onboarding.

Example future files:

```txt
docs/
  support-automation-pipeline.md
  project-structure.md
```

---

### `README.md`

Main presentation file of the project.

It should quickly explain:

- what the project does;
- how to install it;
- how to run tests;
- the main architecture;
- how to contribute.

The README is usually the first file someone reads when opening the repository.

---

### `package.json`

Main Node.js project configuration file.

It describes:

- the project name;
- the project version;
- the project description;
- available npm scripts;
- main dependencies;
- development dependencies.

Example scripts:

```json
"scripts": {
  "test": "vitest --globals",
  "test:run": "vitest run --globals"
}
```

This file is the main indicator that the repository is a Node.js project.

---

### `package-lock.json`

Dependency lock file generated by npm.

It stores the exact versions of all installed dependencies, including indirect dependencies.

It ensures that every developer or server can reinstall the same dependency versions with:

```bash
npm install
```

Difference with `package.json`:

```txt
package.json      = describes the main dependencies and project scripts
package-lock.json = locks the exact installed dependency tree
```

Both files should be committed.

---

### `node_modules/`

Local folder containing installed dependencies.

It is generated by:

```bash
npm install
```

It contains the code of installed libraries such as:

- `zod`;
- `vitest`;
- all their internal dependencies.

This folder can be very large.

It must not be committed to GitHub.

It is ignored by Git through `.gitignore`.

---

### `src/`

Source code of the backend.

This folder will contain the real application logic.

Current content:

```txt
src/
  index.js
```

Future content may include:

```txt
src/
  index.js
  schemas/
    supportAnalysis.schema.js
  decision-engine/
    routeSegments.js
    computeCompleteness.js
    runSupportDecisionEngine.js
```

---

### `src/index.js`

Current entry point of the project.

It currently contains a simple `healthCheck` function used to verify that:

- the project structure works;
- exports/imports work;
- tests can call source code correctly.

Current role:

```txt
basic setup validation
```

Later, this file may expose the main backend functions.

---

### `tests/`

Folder containing automated tests.

Tests verify that the code behaves as expected.

Current content:

```txt
tests/
  health.test.js
```

Future content may include:

```txt
tests/
  routeSegments.test.js
  computeCompleteness.test.js
  runSupportDecisionEngine.test.js
```

---

### `tests/health.test.js`

Basic test file for the current setup.

It calls the `healthCheck` function from `src/index.js` and verifies that the returned object is correct.

This test confirms that:

- Vitest is correctly installed;
- the test script works;
- the source code can be imported;
- the project setup is valid.

## Hidden files and folders

Hidden files are files whose name starts with a dot `.`.

They can be displayed with:

```bash
ls -a
```

Or with a tree view:

```bash
tree -a -I "node_modules"
```

---

### `.git/`

Internal Git folder.

It contains:

- commits;
- branches;
- Git configuration;
- references to remote repositories;
- project history.

This folder is created by:

```bash
git init
```

It should never be manually edited.

If `.git/` is deleted, the folder stops being a Git repository.

---

### `.gitignore`

File used to tell Git which files and folders must not be tracked.

Current ignored items include:

```gitignore
node_modules
dist
.env
coverage
```

Typical ignored files are:

- generated files;
- local dependencies;
- build outputs;
- secret configuration files;
- test coverage reports.

---

### `.env.example`

Example environment configuration file.

It is safe to commit because it does not contain real secrets.

It documents which environment variables are expected by the project.

Example future content:

```env
OPENROUTER_API_KEY=
DATABASE_URL=
NODE_ENV=
```

This file helps another developer understand what variables must be configured locally.

---

### `.env`

Local environment file.

This file does not exist yet by default.

It may be created later to store real local secrets, such as:

```env
OPENROUTER_API_KEY=real-secret-value
DATABASE_URL=real-database-url
```

The `.env` file must never be committed to GitHub.

It is ignored through `.gitignore`.

## npm test commands

### `npm test`

Runs the test script defined in `package.json`:

```json
"test": "vitest --globals"
```

This usually starts Vitest in watch mode.

Watch mode means that Vitest keeps running and automatically reruns tests when files change.

---

### `npm run test:run`

Runs the test script defined in `package.json`:

```json
"test:run": "vitest run --globals"
```

This runs all tests once and then exits.

This command is useful before committing code.

---

### `vitest run --globals`

This is the real command executed behind:

```bash
npm run test:run
```

Meaning:

```txt
vitest   = test framework
run      = run tests once and exit
--globals = make describe, it and expect available globally
```

With `--globals`, test files can use:

```js
describe(...)
it(...)
expect(...)
```

without importing them manually from Vitest.

Vitest automatically detects test files such as:

```txt
*.test.js
*.spec.js
```

For example:

```txt
tests/health.test.js
```

is automatically detected and executed.
